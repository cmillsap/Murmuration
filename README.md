# Murmuration

At dusk in winter, starlings coming in to roost don't land straight away. Tens of
thousands of them gather into a single dark cloud that folds in on itself, splits,
pours through its own gap and snaps back together — a **murmuration**. There is no
leader and no plan. Every bird is just watching a handful of its neighbours and
reacting, and the shape you see is what those small local decisions add up to.

This is that, in a browser, over a hilltop castle at sunset.

**[See it running →](https://cmillsap.github.io/Murmuration/)**

![Thousands of starlings wheeling in front of the setting sun, above a castle silhouetted on a hilltop](screenshot.jpg)

Everything on screen is generated by code when the page loads. There are no model
files, no textures on disk, no images — the hill, the sky, the clouds, the castle and
the birds are all built from maths at startup. The whole thing is one self-contained
`index.html`, about 1,600 lines, with three.js r160 pulled from a CDN. There is no
build step and nothing to install.

The flock itself never touches the CPU. All 4,096 birds (up to 16,384) are simulated
on your graphics card, in shaders, every frame. Most of this README is about how that
works and why it has to be done that way.

---

## Running it

The easiest way is the [live version](https://cmillsap.github.io/Murmuration/).

To run it locally, **double-click `index.html`**. It fetches three.js from a CDN, so
it needs an internet connection, but nothing else.

Some browsers refuse to load JavaScript modules from a `file://` URL. If you get a
blank page and a CORS or module error in the console, serve the folder over HTTP
instead:

```sh
python -m http.server 8765
# then open http://localhost:8765/index.html
```

**Requirements:** any WebGL2 browser from the last few years. If WebGL is missing
entirely you get a plain message instead of a black screen. Two optional features
degrade quietly rather than failing: if floating-point render targets aren't
available the simulation falls back to half-float precision, and if the
post-processing modules fail to load the bloom is switched off and the scene renders
direct.

## Controls

| Input | What it does |
|---|---|
| **drag** | take over the camera; the automatic orbit resumes 4 seconds after you let go |
| **scroll** | zoom in and out |
| **`H`** | show/hide the control panel |
| **`B`** | swap the castle for a church |
| **`P`** | pause the simulation (the camera keeps moving) |

The panel behind `H` has flock size (1,024 / 4,096 / 9,216 / 16,384 birds), live
sliders for the three flocking weights, orbit speed, and toggles for the falcon and
the bloom. It also shows a running FPS counter — useful if you want to find the
largest flock your machine holds at 60fps.

Nudging the sliders is the fastest way to get a feel for the simulation. Drop
**cohesion** to zero and the flock disperses into drifting streamers. Push
**separation** up and it inflates like a balloon. Pull **alignment** down and the
birds stop agreeing on a direction, and the whole thing turns into a swarm of gnats
rather than a flock.

## How the flock works

### The problem

Each bird has to look at other birds to decide what to do. Done naively, every bird
looks at every other bird, which is 4,096 × 4,096 ≈ **16.8 million** neighbour checks
per frame — over a billion per second at 60fps. That is far too much for JavaScript
on the CPU, and it gets four times worse each time you double the flock.

There's a second, quieter problem. Even if the CPU could do the maths, it would then
have to hand 4,096 new positions to the GPU every single frame to draw them. That
upload is its own bottleneck.

Both problems have the same fix: **keep the birds on the GPU and never bring them
back.** The CPU's only job each frame is to set a few numbers — the elapsed time, the
falcon's position, the slider values — and say "go".

### Where the birds live: two textures

A GPU is very good at one specific thing: running the same small program over every
pixel of an image, all at once. So the trick is to stop thinking of the flock as a
list of birds and start thinking of it as **an image where each pixel is a bird**.

The flock is stored in two 64×64 floating-point textures — 4,096 pixels each, one
pixel per bird:

| Texture | R, G, B | A |
|---|---|---|
| **position** | x, y, z in the world | wingbeat phase (0…2π) |
| **velocity** | vx, vy, vz | how hard the bird is banking |

These aren't pictures. They're just grids of numbers that happen to be shaped like a
picture, which is exactly the shape a GPU wants. Change the flock size and you change
the texture size: 32×32 is 1,024 birds, 128×128 is 16,384.

The alpha channels are free real estate. Each texture only needs three of its four
values, so the leftovers carry the wingbeat phase and the bank angle — both computed
in the simulation and read back by the drawing code, so the wings and the roll come
along for free.

### Simulating by drawing

To advance the simulation you draw a full-screen rectangle into a fresh 64×64
texture. The fragment shader runs once per pixel — that is, once per bird — and
whatever it writes becomes that bird's new state. It's an ordinary render pass, but
the output is data rather than a picture.

One catch: a shader can't read and write the same texture at once. So there are two
copies of each, and they swap roles every frame — read from A, write to B, then read
from B, write to A. This is called **ping-ponging**, and it's the standard way to
carry state forward on a GPU.

A frame looks like this:

```
   CPU: dt, time, falcon position, slider values
    │
    ▼
 ┌──────────────────────────────────────────────┐
 │ PASS 1 — velocity shader                     │   for each bird:
 │   read  position[A], velocity[A]             │   sample neighbours,
 │   write velocity[B]                          │   sum up the forces,
 └──────────────────────────────────────────────┘   clamp the turn
    │
    ▼
 ┌──────────────────────────────────────────────┐
 │ PASS 2 — position shader                     │   position += velocity × dt
 │   read  position[A], velocity[B]             │   advance the wingbeat
 │   write position[B]                          │
 └──────────────────────────────────────────────┘
    │
    ▼
 ┌──────────────────────────────────────────────┐
 │ PASS 3 — draw, one instanced call            │   vertex shader looks up
 │   read  position[B], velocity[B]             │   this bird's own pixel
 └──────────────────────────────────────────────┘
    │
    ▼
   swap A and B, repeat
```

Three draw calls a frame for the entire flock, and not one bird position ever crosses
back to the CPU.

### Pass 1: the forces

This is where the behaviour lives. Every force below is computed per bird, per frame,
and summed into one acceleration.

**The three classic flocking rules** (Reynolds' boids, 1986) do most of the work.
Each bird looks at neighbours within a radius and:

- **separation** — steers away from anyone closer than 9 units, harder the closer
  they are. This is the only short-range force, and it's what makes the flock look
  incompressible rather than like a point cloud.
- **alignment** — matches the average heading of neighbours within 22 units. This is
  what turns individual birds into a single moving body.
- **cohesion** — steers toward the average position of neighbours within 44 units,
  which keeps the flock from evaporating.

On their own, those three give you a convincing but slightly dull blob. The rest of
the forces are what make it read as a *murmuration*:

- **A rear blind arc.** A bird ignores anything more than ~114° off its heading — it
  can't see behind itself. This one line matters more than it looks: because
  information only travels forward, a turn started at one edge of the flock
  *propagates* through it as a visible wave rather than happening everywhere at once.
  Those dark ripples rolling across a real murmuration are exactly this.
- **A turn-rate limit and a speed floor.** A bird can change heading by at most 2.9
  radians per second and must fly between 26 and 48 units/s. Course changes become
  arcs instead of snaps, and no bird ever stalls in mid-air.
- **A roost lure.** A slack leash toward a point that wanders on a slow figure-eight
  above the hilltop. It's nearly weightless nearby and firms up sharply once a bird
  strays past ~130 units, so the flock has somewhere to *be* without feeling tethered.
  The vertical component of that leash is weighted 3.2× the horizontal, which squashes
  the flock into the wide, shallow sheet real starlings form instead of a ball.
- **A flow field.** Two octaves of slowly-evolving sine turbulence, sampled from each
  bird's position. Boid rules alone give an evenly-grained cloud; this is what breaks
  it into lobes, filaments and eddies.
- **A falcon.** Birds within 78 units of the predator flee hard, with a slight upward
  bias — the same reflex that opens the expanding holes you see in real footage. The
  falcon itself flies an orbit whose radius breathes in and out, so it alternates
  between wide passes and dives straight through the middle.
- **A floor and a ceiling.** The floor isn't flat — it's a dome that rises over the
  hill, matching the terrain's shape, so birds can dip low out over the plain but
  never clip the castle. A soft ceiling at 435 units keeps them from climbing out of
  frame.
- **A little steady wind**, so the flock drifts rather than sitting in place.

Two details worth flagging. **Separation is scaled by `population / samples`** —
because it accumulates a sum over sampled neighbours rather than an average, it has to
be scaled back up to stay unbiased no matter how many neighbours were checked.
Alignment and cohesion are already averages and need no correction. And **the bank
angle is derived from the sideways component of the acceleration**, smoothed over time
and stashed in the velocity texture's alpha channel, so the visual roll is a
consequence of the physics rather than an animation layered on top.

### Pass 2: position

Trivial next to pass 1: add velocity × dt to position, and advance the wingbeat phase
at a rate that scales with speed, so faster birds flap faster.

### Pass 3: drawing 4,096 birds in one call

Each bird is four triangles — body, tail, two wings — with a `wingFlag` marking which
vertices belong to a wing. That single tiny mesh is drawn 4,096 times in **one
instanced draw call**.

Each instance carries one piece of data: the UV coordinate of its own pixel in the
state textures. The vertex shader reads position and velocity from there and does the
rest of the work itself:

1. Builds an orientation from the velocity — forward along the direction of travel,
   with right and up derived from it.
2. Rolls that frame by the bank angle, so the bird leans into its turns.
3. Rotates the wing vertices around the body axis by `sin(phase)`, so it flaps. Both
   wings beat together because the rotation is signed by which side the vertex is on.
4. Places the vertex in the world.

The flock is marked as never frustum-culled, since the CPU has no idea where any of
these birds actually are.

### The neighbour problem, and the way out

Back to the 16.8 million checks. The fix is to **not look at everyone every frame**.

Each bird samples a fixed 1,024 neighbours per frame, picked as an evenly-spaced comb
across the whole population — start at some index and step by a fixed stride. Two
details make this work:

- **The stride is chosen coprime with the population size.** If it shared a factor
  (say, stride 16 into 16,384 birds), the comb would only ever hit one sixteenth of
  the flock and re-visit it forever. Coprime guarantees the walk can reach every bird.
  The code computes `round(count / samples)` and then bumps it upward until
  `gcd(stride, count) == 1`.
- **The starting point rotates every frame.** The comb slides, so each bird sees a
  different slice each frame, and over a handful of frames it has effectively seen the
  whole flock. Nothing is systematically ignored.

At 4,096 birds that's 4.2 million samples per frame instead of 16.8 million. At 16,384
birds it's still 16.8 million rather than 268 million — the cost per bird stays flat as
the flock grows, which is what makes the larger presets possible at all.

The nice part is that this isn't purely a performance hack. Sampling a *fixed number
of partners* rather than everything inside a fixed radius is closer to how starlings
actually behave. Field studies have found that a starling tracks roughly its seven
nearest neighbours regardless of how far away they are — interaction that's
**topological** rather than metric. That's part of why a real murmuration can compress
and expand dramatically without falling apart, and this sampling scheme has a bit of
the same character.

## The rest of the scene

The flock is the point, but it needs somewhere to be. Everything here is procedural —
generated in code at load time, with no external assets.

**The sky** is a single shader on a large inverted sphere that follows the camera. A
vertical gradient runs from a deep blue zenith through a mauve mid-band to a hot
orange horizon, and three powers of the sun-direction dot product stack on top: a
broad haze across the whole sunward half of the sky, a tighter glow, and the sun's own
aureole. The haze is strongest near the horizon, where light travels through the most
air. The sun disc itself is drawn at 3.4× white — deliberately far brighter than the
display can show — so the bloom pass has something to catch. A touch of dither is added
at the end, because a smooth gradient like this bands visibly on 8-bit output.

**The terrain** is a polar mesh rather than a square grid: 230 rings × 256 sectors,
with ring spacing that starts dense at the centre and stretches cubically outward, so
the hill gets fine detail while the same unbroken surface still reaches 9,000 units to
the horizon. No seams, no LOD popping. The height is a broad Gaussian dome, plus
fractal noise for rolling country (damped near the summit so the hill keeps a clean
silhouette), with a flat plateau carved at the top for the building to stand on and a
gradual flattening toward the far horizon. Vertex colours are picked by height and
slope — low ground darker, summit drier, steep faces rocky — with subtle noise mottling
on top.

**The castle and the church** are assembled from boxes, cylinders and cones: curtain
walls, crenellations placed along each run, corner towers with conical roofs, a
gatehouse, a keep with lit windows, a stair turret and a flag. The flag is the one
thing still animated on the CPU — it's a 12×5 plane, cheap enough to wave by hand.
Press `B` to swap in the church, which has a nave, side aisles, buttresses, an apse and
a spire.

**The clouds** are roughly 2,200 instanced billboards, clustered into 58 groups with
dense cores. The puff texture is fractal noise drawn into a canvas at startup. Their
shading is a cheap fake single-scatter: each puff knows which way it sits relative to
its cluster's centre, and puffs facing the sun are lit while the ones behind stay dark
— enough to give a cluster a real sunset rim. Looking through a cloud toward the sun
adds a silver lining. Above them sits a thin animated cirrus sheet.

**The light** is one warm directional sun casting 4K shadows, plus a cool hemisphere
fill and a dab of ambient, so the shadowed sides read as blue rather than black. The
same `SUN_DIR` vector drives the sun disc, the sky scattering, the cloud shading, the
bird shading and the shadow direction — change that one line and the whole scene's time
of day moves together. Exponential-squared fog tinted to match the horizon colour makes
distant terrain dissolve into the sky rather than ending at a visible edge. Finally,
ACES filmic tone mapping and an unreal-bloom pass on the sun.

**The camera** orbits slowly, drifting in elevation and distance on two slow sines so
it never looks locked to a rail. It opens facing the sun, so the flock and the castle
are backlit from the first frame. Its target eases toward the wandering roost, which
keeps both the flock and the building in frame as the flock drifts. Drag or scroll and
you take over; it hands control back 4 seconds after you stop.

## Code map

`index.html` is numbered into sections. If you want to change something:

| Section | Line | What's there |
|---|---|---|
| 1. Config | 96 | **Start here.** Flock size, all flocking distances and weights, speed limits, roost height, sun angle, the whole colour palette |
| 2. Renderer / scene / camera | 150 | Tone mapping, fog, float-texture capability check |
| 3. Noise | 183 | Shared value noise + fbm |
| 4. Sky + sun | 218 | The sky shader |
| 5. Clouds | 287 | Puff texture, billboard clusters, cirrus |
| 6. Terrain | 525 | Height function and the polar mesh |
| 7. Buildings | 620 | Castle and church |
| 8. Lighting | 853 | Sun, shadows, fill light |
| 9. GPGPU flocking | 875 | **The core.** Compute shaders, ping-pong targets, bird geometry and the render shaders |
| 10. Predator | 1374 | Falcon mesh and its flight path |
| 11. Camera rig | 1422 | Auto-orbit and mouse control |
| 12. Post-processing | 1489 | Bloom |
| 13. UI | 1517 | Panel bindings, keyboard shortcuts |
| 14. Loop | 1577 | Per-frame update order |

The most rewarding place to poke is the `VELOCITY_FS` shader in section 9 — it's the
whole behaviour of the flock in about 100 lines of GLSL. The flow-field block and the
roost leash are the two that change the character of the murmuration most.
